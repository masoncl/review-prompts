# MM Large Folios, THP, and Hugetlb

## Large Folio State Tracking

Misunderstanding which flags are per-page vs per-folio leads to bugs where code
checks or sets state on the wrong struct page. A common mistake is assuming all
flags work like small pages when operating on subpages of a large folio.

The Tracking Level column indicates where the state lives. **Per-folio** means a
single value on the head page applies to the entire folio. **Per-page** means
each subpage carries its own independent value. **PTE-level** means the state is
in the page table entry, not in struct page at all. **Mixed** means the
granularity depends on how the folio is mapped.

| State | Tracking Level | Details |
|-------|---------------|---------|
| PageAnonExclusive | **Mixed** | Per-page for PTE-mapped THP; per-folio (head page) for PMD-mapped and HugeTLB (see `PG_anon_exclusive` in `include/linux/page-flags.h` and `RMAP_EXCLUSIVE` handling in `__folio_add_anon_rmap()` in `mm/rmap.c`) |
| PG_hwpoison | **Per-page** | Marks the specific corrupted subpage (`PF_ANY`); distinct from `PG_has_hwpoisoned` (first tail page) which only indicates at least one subpage is poisoned. Both needed: per-page flag identifies which page, per-folio flag enables fast folio-level check |
| PG_dirty | **Per-folio** | Single flag on head page via `PF_HEAD` policy; PTE-level dirty bits tracked separately in page table entries |
| Accessed/young | **PTE-level** | Tracked in page table entries, not in struct page (apart from the `PG_young`/`PG_idle` folio flags under `CONFIG_PAGE_IDLE_FLAG` on 64-bit); folio-level `PG_referenced` on head page is a separate LRU aging flag |
| Reference count | **Per-folio** | Single `_refcount` on head page shared by all subpages (see `folio_ref_count()` in `include/linux/page_ref.h`) |
| Mapcount | **Per-page** | Each subpage has `_mapcount` by default; `CONFIG_NO_PAGE_MAPCOUNT` (experimental) eliminates per-page mapcounts, using only folio-level `_large_mapcount` and `_entire_mapcount` (see `include/linux/mm_types.h`) |

**Page flag policies** control which struct page within a folio carries each flag.
Using the wrong page silently reads stale data or corrupts unrelated state. See
the "Page flags policies wrt compound pages" comment block in `include/linux/page-flags.h`:
- `PF_HEAD`: flag operations redirect to head page (Dirty, LRU, Workingset;
  most other head-page flags are declared with
  `FOLIO_FLAG(..., FOLIO_HEAD_PAGE)` and have folio-only accessors)
- `PF_ANY`: flag is relevant for head, tail, and small pages
- `PF_NO_TAIL`: modifications only on head/small pages, reads allowed on tail
- `FOLIO_SECOND_PAGE`: flag stored in the first tail page, declared with
  `FOLIO_FLAG()` (`PG_has_hwpoisoned`, `PG_large_rmappable`,
  `PG_partially_mapped`). The `PF_SECOND` policy macro is still defined but no
  flag uses it

**Atomic vs non-atomic page flag operations:**

Non-atomic flag operations (`__set_bit()` / `__clear_bit()`, generated by
`__FOLIO_SET_FLAG()` / `__FOLIO_CLEAR_FLAG()` in `include/linux/page-flags.h`)
perform a read-modify-write on the entire `unsigned long` flags word. They are
only safe when the caller has exclusive access to the whole flags word -- not
merely when access to the individual bit is serialized by a lock. Multiple page
flags share the same `unsigned long`, so a lock that serializes one flag does
NOT protect against concurrent modification of a different flag in the same
word by code running under a different lock.

This is especially important for the flags stored on the first tail page
(`FOLIO_SECOND_PAGE`): `PG_has_hwpoisoned`, `PG_large_rmappable`,
`PG_partially_mapped`, and `PG_anon_exclusive` (via `PF_ANY` on tail pages) all
share the same flags word and are modified by different subsystems under
different locks.

**REPORT as bugs**: Code that uses non-atomic page flag operations
(`__folio_set_*` / `__folio_clear_*` / `__SetPage*` / `__ClearPage*`) on a
page whose flags word can be concurrently modified by another code path,
unless the caller holds exclusive access to the entire page (e.g., during
allocation before the page is visible, or during final freeing).

## Compound Page PFN Natural Alignment

An order-`n` compound page starts at a PFN naturally aligned to `1 << n`.
Any subpage PFN in that compound page rounds down to the same head PFN with
`pfn & ~((1UL << order) - 1)` or `ALIGN_DOWN(pfn, 1UL << order)`.

## Page Cache Reference Counting for Large Folios

`__filemap_add_folio()` in `mm/filemap.c` adds `folio_nr_pages(folio)` extra
references. A page-cache folio's refcount = `folio_nr_pages()` (page cache) +
one per other holder, including the caller's own reference; an idle page-cache
folio has refcount == `folio_nr_pages()`, plus one if `PG_private` is set (see
`folio_expected_ref_count()`). Removal must drop all page-cache refs via
`folio_put_refs(folio, folio_nr_pages(folio))` (see `filemap_free_folio()` in
`mm/filemap.c`). Using `folio_put()` (single-ref drop) after
`__filemap_remove_folio()` leaks `folio_nr_pages() - 1` refs -- a silent memory
leak only visible with large folios.

## Large Folio Split Minimum Order

Splitting a file-backed large folio below the mapping's minimum folio order
fails with `-EINVAL`. Callers that assume a successful split always yields
order-0 folios will hit warnings, operate on unexpectedly large folios, or
mishandle error paths on LBS (large block size) filesystems.

File-backed address spaces can set a minimum folio order via
`mapping_set_folio_min_order()` (see `mapping_min_folio_order()` in
`include/linux/pagemap.h`). The split infrastructure in `__folio_split()` in
`mm/huge_memory.c` enforces this: if `new_order < min_order`, the split returns
`-EINVAL`.

**Split API behavior:**
- `split_huge_page()` and `split_folio_to_list()` always request order-0.
  They will fail for file-backed folios whose mapping has min order > 0.
- `folio_split()` in `mm/huge_memory.c` takes an explicit `new_order` and a
  `split_at` page. It splits non-uniformly: the folio containing `split_at`
  ends up at `new_order` and the rest stays as large as possible. Use
  `min_order_for_split()` to get the lower bound of `new_order`.
- `min_order_for_split()` in `mm/huge_memory.c` returns
  `mapping_min_folio_order(folio->mapping)` for file-backed folios and 0 for
  anonymous folios (also 0 for a file folio that has already been truncated,
  `folio->mapping == NULL`).

**Review checklist for folio split callers:**
- If code calls `split_huge_page()` or `split_folio_to_list()` and then
  assumes the result is order-0 (e.g., `WARN_ON(folio_test_large(folio))`),
  verify it handles `-EINVAL` from mappings with min order > 0
- If code needs to split to the lowest possible order, it must call
  `min_order_for_split()` first and pass that order explicitly to
  `folio_split()` or `split_huge_page_to_list_to_order()`
- After a successful split to non-zero order, the resulting folios are still
  large (`folio_test_large()` returns true); code must not assume they are
  base pages

## Large Folio Split Refcount Precondition

Calling `split_folio()` on a large folio while extra references are held
causes it to return -EAGAIN, and if the caller retries in a loop, this
creates a livelock that only manifests under contention from multiple tasks
operating on the same folio.

`split_folio()` reaches `__folio_split()` in `mm/huge_memory.c`, which checks
`folio_expected_ref_count(folio) != folio_ref_count(folio) - 1`. The expected
count is computed by `folio_expected_ref_count()` in `include/linux/mm.h`,
summing references from mapcount, page cache, swap cache, and `PG_private`.
The `- 1` accounts for the single caller pin. Any additional `folio_get()`
references -- such as those held by other tasks blocked on `folio_lock()` --
cause this check to fail.

**Dangerous under contention (refcount before lock, then retry):**
```c
// RISKY if retried: raises refcount, then blocks on lock; other tasks
// doing the same inflate the refcount, causing split_folio() to fail
folio_get(folio);
folio_lock(folio);          // blocks while holding extra ref
err = split_folio(folio);   // -EAGAIN while others hold references
```

**Safe ordering (lock before refcount):**
```c
// CORRECT: lock first so only one task proceeds; then raise refcount
if (!folio_trylock(folio))
    return -EAGAIN;         // no refcount raised, no livelock
folio_get(folio);
err = split_folio(folio);   // expected refcount matches
```

See `madvise_free_huge_pmd()` in `mm/huge_memory.c` for the correct
lock-before-refcount pattern when splitting is needed.

**REPORT as bugs**: Code that takes `folio_get()`, blocks in `folio_lock()`,
calls `split_folio()`, and on `-EAGAIN` retries the same folio without bound
(directly or by restarting the walk) when several tasks can do this
concurrently. A single attempt, or a bounded number of attempts, whose failure
is handled by skipping, falling back or returning is fine.
`try_to_split_thp_page()` in `mm/memory-failure.c` holds a reference, blocks on
the lock and tries once. `try_split_folio()` in `mm/migrate.c` blocks for
non-`MIGRATE_ASYNC` modes, and `migrate_pages_batch()` retries it for
`MR_LONGTERM_PIN`, but at most `NR_MAX_MIGRATE_PAGES_RETRY` passes.

## Large Folio i_size Boundary Checks

Mapping file-backed large folios without checking `i_size` breaks POSIX
SIGBUS semantics: accesses within a VMA but beyond `i_size` rounded up to
`PAGE_SIZE` must generate SIGBUS, but over-mapping a large folio silently
serves zero-filled pages for those accesses instead.

**Invariants:**
- PTEs must not be installed for file pages beyond
  `DIV_ROUND_UP(i_size_read(mapping->host), PAGE_SIZE)`. Code that
  computes the number of PTEs to install from `folio_nr_pages()` or
  `folio_next_index()` must clamp against `i_size`. See
  `filemap_map_pages()` in `mm/filemap.c` which clamps `end_pgoff` to
  `file_end`
- PMD mappings must not be installed when the folio extends past
  `i_size`. Both `filemap_map_pages()` in `mm/filemap.c` and
  `finish_fault()` in `mm/memory.c` compare the end of the file against
  `folio_next_index(folio)` before allowing PMD mapping via
  `filemap_map_pmd()` or `do_set_pmd()`
- On truncate, if a large folio spanning the new `i_size` cannot be
  split, the folio must be fully unmapped so it will be refaulted with
  PTEs (which respect `i_size` clamping). See `folio_split_or_unmap()`
  in `mm/truncate.c`, which calls `try_to_unmap()` on split failure

**Exception -- shmem/tmpfs**: `shmem_mapping()` returns true for shmem/tmpfs
address spaces. These mappings are exempt from the `i_size` boundary check,
both for PMD mapping and for mapping the whole large folio with PTEs, and are
allowed to map across `i_size`. All three enforcement sites
(`filemap_map_pages()`, `finish_fault()`, and `folio_split_or_unmap()`) check
`shmem_mapping()` to preserve this behavior.

## Large Folio Swapin and Swap Cache Conflicts

Large folio (mTHP) swapin must not put a large folio over a range where a
smaller folio is already in the swap cache. The swap cache is tracked in the
swap table, and `swap_cache_alloc_folio()` in `mm/swap_state.c` does the
conflict check, the allocation and the order fallback in one loop: on
`-EBUSY` or `-ENOMEM` it retries at the next lower order in the `orders`
bitmask the caller passed.

Callers may do a single-entry `swap_cache_get_folio()` lookup for a cache
hit, but they do not check the *range* for conflicting smaller folios
themselves; they pass the acceptable orders to `swapin_sync()`. The anonymous
path passes `thp_swapin_suitable_orders(vmf) | BIT(0)` (see also
`can_swapin_thp()` in `mm/memory.c`). `shmem_swap_alloc_folio()` in
`mm/shmem.c` passes a single order and on any error retries once at order 0.
A new large folio swapin path that checks the swap cache and then allocates
separately reopens the race this loop closes. One that retries the same
order on failure can loop forever, because readahead or concurrent swapin
can keep order-0 entries in the cache.

## Hugetlb Folio Type Transition Races

Accessing hugetlb-specific folio metadata (such as calling `folio_hstate()`)
after an unlocked `folio_test_hugetlb()` check causes a NULL pointer
dereference when another CPU concurrently clears the hugetlb type and frees
the folio.

`__update_and_free_hugetlb_folio()` in `mm/hugetlb.c` calls
`__folio_clear_hugetlb()` under `hugetlb_lock`, which clears the hugetlb page
type. After the type is cleared, `folio_hstate()` (in
`include/linux/hugetlb.h`) trips its `VM_BUG_ON_FOLIO(!folio_test_hugetlb())`
(`CONFIG_DEBUG_VM` only), and once the folio has been freed and reused at
another order `folio_size()` no longer matches a registered hstate, so
`size_to_hstate()` returns NULL.

```c
// WRONG: TOCTOU race
if (folio_test_hugetlb(folio)) {
    h = folio_hstate(folio);  // type may be cleared, folio freed and reused
}

// CORRECT: Check and use under the same lock
spin_lock_irq(&hugetlb_lock);
if (folio_test_hugetlb(folio)) {
    h = folio_hstate(folio);
}
spin_unlock_irq(&hugetlb_lock);
```

An unlocked `folio_test_hugetlb()` is acceptable as a preliminary fast-path
filter (to avoid taking the lock), but the result must not be trusted for
subsequent hstate derivation without re-checking under the lock, unless the
caller holds a reference on the folio or otherwise owns it (mapped,
isolated): the hugetlb type is only cleared on folios with refcount 0. Code
outside `mm/hugetlb.c` that encounters hugetlb pages through lockless PFN
iteration (such as `page_is_unmovable()` in `mm/page_isolation.c`) must use
`size_to_hstate()` with a NULL check instead of `folio_hstate()`.

## Hugetlb Fault Path Locking

Lock ordering: `hugetlb_fault_mutex` -> hugetlb vma lock -> `i_mmap_rwsem` ->
`folio_lock` (see `mm/rmap.c` comment block). The hugetlb vma lock
(`hugetlb_vma_lock_read()` / `hugetlb_vma_lock_write()`) is a separate lock
from the per-VMA lock (`vma_start_read()`), which hugetlb faults may also hold.
`hugetlb_wp()` drops the mutex and the hugetlb vma lock mid-operation (to call
`unmap_ref_private()`, which needs the vma lock in write mode) and then retakes
them. That drop only happens for a COW by the mapping's owner, so the old
folio is always anonymous.

`hugetlb_fault()` keeps the anon folio locked across `hugetlb_wp()`, including
that drop. While the mutex is released another faulter on the same folio takes
the mutex and then wants the folio lock, so this is safe only because every
path that locks an anon hugetlb folio under the fault mutex uses
`folio_trylock()`, sets `need_wait_lock`, and calls `folio_wait_locked()` after
all locks are dropped. A blocking `folio_lock()` on an anon hugetlb folio under
the mutex is an ABBA deadlock; see the comment near the end of
`hugetlb_fault()`.

A blocking lock under the mutex is fine for pagecache folios, provided it is
not held across `hugetlb_wp()`: `hugetlb_no_page()` calls
`filemap_lock_hugetlb_folio()` under the mutex but unlocks the file folio
before calling `hugetlb_wp()`. Prefer testing folio state without locking when
possible (e.g., `folio_test_anon()` does not need the folio lock).

## Hugetlb Pool Accounting

`struct hstate` (`include/linux/hugetlb.h`) has four counters (all
protected by `hugetlb_lock`): `nr_huge_pages` (total), `free_huge_pages`,
`surplus_huge_pages` (beyond persistent pool), `resv_huge_pages` (reserved).
Available = `free_huge_pages - resv_huge_pages` (see `available_huge_pages()`).
Each has per-node variants except `resv_huge_pages`.

**Key rules:**
- `alloc_hugetlb_folio()` gets `map_chg` from `vma_needs_reservation()`.
  `gbl_chg` is 0 when the vma reservation is reused, otherwise the return of
  `hugepage_subpool_get_pages()` (also 0 when the subpool's own reserve covers
  the page). `gbl_chg == 0` selects `HUGETLB_ALLOC_USE_GLOBAL_RESERVATIONS`, and
  only then does `hugetlb_alloc_folio()` decrement `resv_huge_pages` and set
  `HPG_restore_reserve`
- Derived values (`persistent_huge_pages()` = `nr_huge_pages -
  surplus_huge_pages`) combine counters that must be updated in the same
  `hugetlb_lock` hold to avoid transient inconsistency
- `remove_hugetlb_folio()` / `add_hugetlb_folio()` take `bool adjust_surplus`,
  which decides whether `surplus_huge_pages` (and its per-node counter) moves
  with `nr_huge_pages`. A constant is correct when the surplus count must not
  move or the folio is known to be (non-)surplus, e.g. demote, one-for-one
  replacement, temporary folios, vmemmap-restore failure,
  `return_unused_surplus_pages()`. Where the page may be either, the caller
  decides from `h->surplus_huge_pages_node[nid]` (see
  `dissolve_free_hugetlb_folio()` and `free_huge_folio()`). An error path that
  re-adds a folio must pass the same value the forward path used

## Hugetlb PMD Page Table Sharing and Unsharing

Unsharing a hugetlb PMD table does not free it. `huge_pmd_unshare()` clears
the PUD and records the unshare in the `struct mmu_gather` with
`tlb_unshare_pmd_ptdesc()`, which sets `unshared_tables` and, when this was the
last sharer, `fully_unshared_tables`. The caller must then call
`huge_pmd_unshare_flush()` before dropping `i_mmap_rwsem`. That flushes the
TLB and, for `fully_unshared_tables`, calls `tlb_remove_table_sync_one()`,
which sends an IPI to wait for GUP-fast walkers (they run under
`local_irq_save()`) before the now-exclusive table can be reused. The bug to
look for is a missing `huge_pmd_unshare_flush()`, not a missing
`tlb_remove_table()`.

**Locking:** `huge_pmd_unshare()` requires `i_mmap_rwsem` held for write plus
the hugetlb vma lock (write mode per its kernel-doc); both are asserted in
`__huge_pmd_unshare()`, though the vma lock assert only checks that it is held.
`huge_pmd_share()` takes `i_mmap_rwsem` for read internally; its callers
(`huge_pte_alloc()` from the fault path) hold only the hugetlb vma lock in
read mode. See both functions in `mm/hugetlb.c`.

## Memory Failure Folio Handling

**`memory_failure()` return values** (`mm/memory-failure.c`): `0` = recovered
(no signal needed), `-EHWPOISON` = already poisoned (also returned when a large
folio could not be split to order 0), `-EOPNOTSUPP` = filtered by
`hwpoison_filter()`, other negative = recovery failed (the arch caller decides
whether to kill the process). Architecture MCE handlers (`kill_me_maybe()` in
`arch/x86/kernel/cpu/mce/core.c`) branch on these. Internal helpers whose
returns propagate through `memory_failure()` must return `0` for successful
recovery, not `-EFAULT`.

**Large folio hwpoison:** `PG_hwpoison` is per-page (`PF_ANY`);
`PG_has_hwpoisoned` is per-folio (first tail page) as a fast indicator. Both
must stay synchronized. When splitting a poisoned folio, `PG_has_hwpoisoned`
must propagate to the correct sub-folio. Re-check `folio_test_large()` after
acquiring folio lock (concurrent split possible). Hugetlb is different: it
never sets `PG_has_hwpoisoned`, it sets `PG_hwpoison` on the head page only,
and it records the raw subpages in the folio's `_hugetlb_hwpoison` list.

**HWPoison content access guard:** accessing poisoned page content triggers
an unrecoverable MCE/panic. Check `PageHWPoison(page)` per-subpage (to skip
individual pages) or `folio_contain_hwpoisoned_page(folio)` for early-exit
before any content access (`pages_identical()`, `copy_page()`,
`kmap_local_page()` + read, etc.). **REPORT as bugs**: content reads in THP
split, migration, KSM, or compaction without hwpoison checks.

## Quick Checks

- **Large folio mapcount field consistency**: `_large_mapcount`,
  `_entire_mapcount`, per-page `_mapcount`, `_nr_pages_mapped` are updated
  by separate operations in rmap code. `folio_lock_large_mapcount()`
  serialises `_large_mapcount` with the per-MM `_mm_id_mapcount[]` / `_mm_id[]`;
  it does not make `_entire_mapcount`, per-page `_mapcount` or
  `_nr_pages_mapped` consistent with them. See
  `__wp_can_reuse_large_anon_folio()` in `mm/memory.c`: optimistic check,
  lock, recheck, act
- **Large folio boundary spanning in PFN iteration**: large folios crossing
  sub-range boundaries are seen in multiple sub-ranges. Without dedup,
  actions apply multiple times (double pageout, inflated stats). Track
  last-processed folio or advance by `folio_size()`. See `last_applied` in
  `struct damos`
- **Large folio size preconditions on hwpoison paths**: `unmap_poisoned_folio()`
  cannot handle large non-hugetlb folios. Callers must check
  `folio_test_large() && !folio_test_hugetlb()` and split or skip the folio
  before calling. `memory_failure()` splits via `try_to_split_thp_page()`
  first; `do_migrate_range()` and `shrink_folio_list()` skip it
- **Hugetlb page cache insertion protocol**: before
  `hugetlb_add_to_page_cache()`: zero with `folio_zero_user()`, mark
  uptodate with `__folio_mark_uptodate()`, hold
  `hugetlb_fault_mutex_table[hash]`. Not enforced by the function itself.
  See `hugetlbfs_fallocate()` in `fs/hugetlbfs/inode.c`
- **Hugetlb HPG flag propagation during demotion**: `init_new_hugetlb_folio()`
  does NOT propagate HPG flags from `folio->private`. Allocation-origin flags
  like `HPG_cma` control the deallocation path (CMA vs buddy). Code creating
  new hugetlb folios from an existing one must explicitly copy these flags.
  See `demote_free_hugetlb_folios()` in `mm/hugetlb.c`
- **Hugetlb folio rejection in generic folio paths**: generic rmap/migration
  callbacks that only handle PTE-level folios must reject hugetlb early via
  `folio_test_hugetlb()`. Hugetlb requires distinct PTE ops, rmap functions,
  RSS accounting, and locking. Compare `try_to_unmap_one()`/
  `try_to_migrate_one()` in `mm/rmap.c` (full hugetlb branches) against new
  callbacks
- **Hugetlb subpool reservation rollback**: `hugepage_subpool_get_pages()`
  absorbs some pages from `rsv_hpages` and returns smaller `gbl_reserve`.
  Error paths must return `chg - gbl_reserve` (not `chg`) to
  `hugepage_subpool_put_pages()`, and feed its return to
  `hugetlb_acct_memory()`. Over-crediting causes `resv_huge_pages` underflow
- **Deferred split queue for large folios**: partial unmap of an *anonymous*
  large folio is queued for deferred split inside `__folio_remove_rmap()` in
  `mm/rmap.c`. Callers of `folio_remove_rmap_pte()` / `folio_remove_rmap_pmd()`
  need not, and should not, call `deferred_split_folio()` themselves. Code
  that bypasses those helpers, or that moves a partially mapped folio (see
  `mm/migrate.c`), must preserve the queueing, or the partially-mapped folio
  wastes memory until it is fully unmapped
- **`try_to_unmap()` on PMD-mapped large folios**: requires
  `TTU_SPLIT_HUGE_PMD` flag, otherwise `VM_BUG_ON_FOLIO(!pvmw.pte, folio)` fires in
  `try_to_unmap_one()`. A PMD-mapped lazyfree folio is the exception, handled
  by `unmap_huge_pmd_locked()` before that check. Wrappers like
  `unmap_poisoned_folio()` do NOT set this flag — callers must guarantee not
  a large folio (except hugetlb)
- **`pmd_trans_huge()` matches both THP and hugetlb PMDs**: check
  `is_vm_hugetlb_page(vma)` first before THP-specific operations
  (`split_huge_pmd()`, `pgtable_trans_huge_withdraw()`). Hugetlb uses
  different page table layout, locking, and splitting semantics. Same
  ambiguity at PUD level
- **Memory failure accounting consistency**: `action_result()` updates
  `num_poisoned_pages` (global) and `struct memory_failure_stats` (per-node)
  together in `memory_failure()` handling paths. Calling
  `num_poisoned_pages_inc()` there without `update_per_node_mf_stats()` causes
  `/proc/meminfo` vs sysfs inconsistency. Soft offline (`page_handle_poison()`)
  intentionally bumps only `num_poisoned_pages`
